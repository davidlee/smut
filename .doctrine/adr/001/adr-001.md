# ADR-001: Identity is `smut_id`, not `id`

Status: **proposed** — recorded from operator direction on 2026-11-01, rationale
revised on review (RV-022 F-2), held open for the operator's acceptance act. The
direction, in the operator's words: "we should use `smut_id` not `id`. It loses
slightly in brevity but solving the collision issue is worth more, and `smut_id` is
not too bad to type and will never conflict with anything."

## Context

`id` expresses identity in every value tree smut touches: an entity is an object
with a string `id` (DEC-005), a reference anywhere at any depth is `{"id": "..."}`,
an entity file holds its `id`, and `select`/`where`/`follow` name fields inside
those objects. That makes `id` the one key a caller can never use for their own
data.

Three consequences, all recorded as backlog:

- **ISS-002** — a payload's own `id` cannot be stored. Measured: a nested
  `{"id":"abc","name":"Ext"}` silently declares an entity and strips the payload
  down to `{"id":"abc"}`; a nested `{"id":"zzz"}` is a reference reported
  `missing`; a nested `{"id":null}` or `{"id":7}` refuses the whole batch at exit
  2. `id` is the most likely key in JSON copied from anywhere else.
- **ISS-003** — generation happens only for a declaration root, so a nested entity
  must be *named* at the moment of writing. That is an authoring question in its own
  right: **it is independent of the key spelling** (prechosen ids author a cyclic
  graph in one batch today), and settling it does not depend on this ADR.
- **IDE-002** — ids cannot be renamed, so a name chosen badly is permanent. This
  ADR does not change that and does not answer it.

ISS-002 is the item this ADR decides. ISS-003 and IDE-002 are recorded here only so
that a reader of one knows the others exist: minting is additive and independent,
and a reference-preserving rename stays deferred (it would be an additive verb
too — nothing in this ADR forecloses it).

## Decision

The identity key is `smut_id`. Everywhere identity is expressed inside stored or
declared data — the entity's own identity, and every reference — the key is
`smut_id`. Bare `id` becomes ordinary data at any depth, with no reservation and no
special case.

## Why

- **The failure being repaired is specific, and silent.** Today the key `id`
  decided by *proximity* whether a value is data or graph: an imported payload
  carrying `id` plus any sibling field silently becomes a new entity and leaves a
  reference behind, and a payload carrying `id` alone silently becomes a reference
  to something that may not exist. Neither is refused; both restructure the graph
  the caller thought they were storing. Namespacing identity fixes that class of
  failure at its cause — the reserved key stops being the one key a caller is most
  likely to be carrying for their own reasons.
- **A namespaced reservation is proportional; a bare one is not.** The store must
  reserve *something*, because an entity's own identity has to be recognisable in a
  value tree. Reserving `smut_id` keeps the reservation and makes it collide only
  with a key nobody's payload has, which is the proportionate version of the rule
  rather than the absence of one.
- **The brevity cost is small and one-directional.** Five extra characters, typed
  rarely (mostly pasted), against a reservation that never stops costing. `smut_id`
  also reads as exactly what it is, which `id` inside an entity file never quite
  did.

## Alternatives rejected

- **Keep `id`, document the limit.** A permanent papercut on the most likely key,
  in a store whose selling point is permissiveness.
- **Placeholders (`{"$ref0": ...}`) or a declare-me marker key.** Both reserve
  another spelling to solve what the first spelling's reservation caused. Operator's
  verdict, which this record adopts: "cleverness which only amounts to a partial
  solution."
- **Type-dependent disambiguation** (a non-string `id` is data). Half a fix: it
  removes the exit-2 case alone, and makes identity depend on a value's type rather
  than on the key.

## Consequences

- **A format break, deliberately unmitigated.** Entity files, every stored
  reference, the fixture store and the versioned store-format document all carry
  `id` today. The store's format version moves and the loader refuses an older
  store by version, naming what it read and what it reads. Operator direction:
  "we're not writing a migration script, let alone legacy handler. blow up
  loudly." So there is no dual-key reader, no migration verb and no repair path —
  which is also the standing rule that validation reports a store and never fixes
  it, applied to a version rather than to a corrupt entry.
- **Minting is independent of this decision, and its race is accepted.** A minting
  verb supplies generated ids for a caller to declare with; that works under either
  spelling (`ISS-003`), so nothing here depends on it. If it is adopted, a minted id
  is not reserved, so a store that gains that id between minting and declaring turns
  the declaration into an upsert — expected never to occur in smut's lifetime, noted
  for completeness rather than as a design driver.
- **The envelope follows, on one rule: an entity object carries `smut_id`.**
  Entity-shaped objects carry it wherever they appear — files, `objects[]`,
  `changes[].previous`, the `conventions --format json` declaration. So do
  references (`{"smut_id": ...}`) at any depth. And `changes[]` names its subject
  `smut_id` rather than `id`, which makes it the one envelope key that changes.

  The rule is drawn at *is this object an entity?*, not at *is this value an id?*,
  because the second line cannot be held: `ids`, `deleted`, `missing`, `frontier`,
  `depths` (keyed by id), `edges[].source`/`.target` and `dangling[].source` all
  carry identity without a key that spells it, and they keep their names.

  Why the mixed alternative was rejected, since it is the obvious one: an envelope
  name is *read-only*, while a field name also works in `where`, `select` and
  `follow`. Under mixed naming the same value has two names, one writable and one
  not, and using the wrong one fails silently — a missing field fails every
  predicate operator except `$exists`, so `where: {"id": ...}` after the rename
  returns an empty result at exit 0, which reads as "nothing matched" rather than
  "wrong key". The guide's own two-call recipe filters on `id` today, so the
  documentation would teach both spellings for the same value. Prettiness that does
  not survive the first wrong `where` is not worth a second name for identity.

  The cost is coupling: the response vocabulary now carries the store's field name,
  so a future respelling would churn consumers. Accepted — a name that is writable
  is *meant* to be tracked by consumers, and `previous` already puts a whole entity
  inside `changes[]`, so the change record is visibly about an entity.
- **`smut learn`, the README and every example** carry `"id"` today, so the human
  surface moves with the format.

## The boundaries this leaves

This decision moves the reservation and narrows it; it does not make the store hold
arbitrary JSON. Stated explicitly, because promising more than the format can keep
is how the next surprise gets built:

- **`smut_id` is structural at every depth.** An object anywhere in a declaration
  with a string `smut_id` member is an entity or a reference, at any nesting level.
  A payload carrying its own `smut_id` — vanishingly unlikely, and namespaced
  precisely so — is still read as graph. Some key has to be, and this one is chosen
  to be the key nobody else uses.
- **The `DROP` sentinel still costs one literal.** The string `"DROP"` as a
  top-level field value means "remove this field" and cannot be stored as a value
  there; a payload storing `"DROP"` under a top-level field name loses it. Nested
  and array occurrences are ordinary values, and this is unchanged by the rename.
- **`null` is ordinary, absence is not.** A stored field whose value is `null` is a
  value; a field that is not there is absent. `$exists` distinguishes them, and will
  distinguish them on `smut_id` too.
- **`$` is reserved one level up.** Predicate objects reserve `$`-prefixed keys
  (`$eq`, `$and`, …), so an embedded object whose keys are operator-shaped has to be
  compared through an explicit `$eq`. Unrelated to this ADR, and unchanged.

So the honest claim is: a caller's own `id` stops being structural, and the one key
that remains structural is one they will not be carrying by accident. Where the
store still cannot hold exactly what a caller brought, the boundaries above say so.

## Status

Proposed. Decided and recorded here: the key (`smut_id` for entity objects and
references, `changes[].smut_id`; container-named id values unchanged), the
unmitigated format break, and the boundaries it leaves standing.

Deliberately *not* decided here, and not dependent on it:

- the minting verb's contract (ISS-003 — settled separately; it works under either
  spelling, costs two invocations for one atomic graph write, and reserves nothing);
- the store format's new version number, which belongs to the slice's design;
- a reference-preserving rename (IDE-002 — stays deferred, and would be additive).

Rationale revised on review: RV-022 F-2 found the first draft claiming that the
reservation disappears and that minting depended on the rename. Both were wrong and
are corrected above — what improves is the collision, not the existence, of a
reserved key.

Awaiting the operator's acceptance act. Not yet implemented.
