# ADR-001: Identity is `smut_id`, not `id`

Status: accepted. Recorded from operator direction on 2026-11-01: "we should use
`smut_id` not `id`. It loses slightly in brevity but solving the collision issue is
worth more, and `smut_id` is not too bad to type and will never conflict with
anything."

## Context

`id` expresses identity in every value tree smut touches: an entity is an object
with a string `id` (DEC-005), a reference anywhere at any depth is `{"id": "..."}`,
an entity file holds its `id`, and `select`/`where`/`follow` name fields inside
those objects. That makes `id` the one key a caller can never use for their own
data.

Three consequences, all recorded as backlog:

- **ISS-002** — a payload's own `id` cannot be stored. Measured: a nested
  `{"id":"abc","name":"Ext"}` silently declares an entity and strips the payload
  down to `{"id":"abc"}`; a nested `{"id":"zzz"}` is a reference reported
  `missing`; a nested `{"id":null}` or `{"id":7}` refuses the whole batch at exit
  2. `id` is the most likely key in JSON copied from anywhere else.
- **ISS-003** — generation happens only for a declaration root, so a nested entity
  must be *named* at the moment of writing. Generated ids are therefore
  unavailable exactly where a graph is authored: wiring takes a second batch.
- **IDE-002** — ids cannot be renamed, so a name chosen badly is permanent, which
  is what makes generated ids the safer policy in the first place.

The three are one question: how identity is expressed in a value tree, and who
chooses the name. They are decided together or not at all.

## Decision

The identity key is `smut_id`. Everywhere identity is expressed inside stored or
declared data — the entity's own identity, and every reference — the key is
`smut_id`. Bare `id` becomes ordinary data at any depth, with no reservation and no
special case.

## Why

- **The store's premise is permissive.** Its job is to hold what a caller brought,
  including JSON from systems that already have their own `id`. A notebook that
  refuses `{"external":{"id":7}}`, or silently restructures it into a new entity,
  fails at that job on the most ordinary key in the format.
- **The brevity cost is small and one-directional.** Five extra characters, typed
  rarely (mostly pasted), against a reservation that never stops costing. `smut_id`
  also reads as exactly what it is, which `id` inside an entity file never quite
  did.
- **It makes the other two decisions cheaper.** With no reserved spelling in the
  value space, a minting verb (`smut new`) can supply generated ids for a whole
  graph with nothing reserved at all — which is the only cure for ISS-003 that
  adds no second identity shape.

## Alternatives rejected

- **Keep `id`, document the limit.** A permanent papercut on the most likely key,
  in a store whose selling point is permissiveness.
- **Placeholders (`{"$ref0": ...}`) or a declare-me marker key.** Both reserve
  another spelling to solve what the first spelling's reservation caused. Operator's
  verdict, which this record adopts: "cleverness which only amounts to a partial
  solution."
- **Type-dependent disambiguation** (a non-string `id` is data). Half a fix: it
  removes the exit-2 case alone, and makes identity depend on a value's type rather
  than on the key.

## Consequences

- **A format break.** Entity files, every stored reference, the fixture store and
  the versioned store-format document all carry `id` today. The store's format
  version moves, and the loader should refuse an older store *by version* with a
  message naming the migration — not accept both spellings. The existing stance
  that store validation never repairs a store, only reports it, argues against a
  tolerant dual-key reader: two spellings of identity is the ambiguity this ADR
  exists to remove.
- **The minting verb makes a race possible and the ADR accepts it.** A minted id is
  not reserved, so a store that gains that id between minting and declaring turns
  the declaration into an upsert. Expected to happen never in smut's lifetime, and
  noted for completeness rather than as a design driver.
- **Envelope vocabulary is a separate question, deliberately left open.** Entity-
  shaped objects should carry `smut_id` wherever they appear (files, `objects[]`,
  `changes[].previous`). Response-only keys — the `ids` array, `changes[].id`,
  `edges[].source`/`target` — are envelope vocabulary rather than entity data, and
  renaming them buys nothing; keeping them is the recommendation, to be settled
  when this is designed rather than here.
- **`smut learn`, README and every example** carry `"id"` today, so the human
  surface moves with the format.

## Status

Recorded from operator direction on 2026-11-01. Not yet implemented; ISS-002,
ISS-003 and IDE-002 remain open and should be planned as one change.
