# RFC-001: Agent usability: what three independently authored stores taught about the query surface

## Context

Two evidence sets arrived a day apart, and they rank the same surface differently.

1. **A 0.2.0 release-candidate trial** — an operator's ~40 probes, reported as five
   frictions. Filed as ISS-004, IMP-008, IMP-009, IMP-010.
2. **A three-store exercise** — three domains (an engineering org, a clinical
   trial, a water distribution network), 34 entities each, authored by
   independently briefed agents that saw neither smut's documentation nor its
   query language. Each author supplied six questions *with expected answers
   computed from its own data*. 18 questions were then answered with the binary:
   18 correct, one of them retracted and re-done because the tool had misled the
   answerer (see IMP-011).

The question this RFC holds open: **what is the order of work on the agent-facing
surface, and which of the two reports are the same finding wearing two coats?**

It is a discussion, not a decision. The ranking below depends on base rates that
neither input measures well, and two of the findings want a design decision before
any implementation. Nothing here asserts canon; it is a mutable planning doc.

## Discussion

### What the exercise measured

| observation | measurement |
| --- | --- |
| discriminator present as the shipped advice recommends (`type`) | 0 of 3 stores; 2 used `kind`; 1 had none; 1 overloaded `kind` with a physical class |
| class filter by id substring | superset: `p-` matched `pump-*` — 4 objects where the question asked for 2, exit 0 |
| absence-of-incoming-reference written as a field test | all 11 where the truth was 6, exit 0 |
| silent empty answers | 2 (wrong field name; wrong discriminator) on top of the superset above |
| traversal root present in a referrer-count answer | always; manual subtraction in 7 of 18 answers |
| `$gt` as the first guess at a range test | 2 of 3 domains; refused by name each time |
| calls per question where a label or a second edge type was needed | up to 3 |
| everything else | 18/18 answers correct; 3 × 34-entity declares lossless; cycles terminated |

### The ranking

Ordered by expected harm — frequency × invisibility × how wrong the answer gets —
with fix cost a tiebreak. The first three fail *silently*; the rest cost calls or
reading.

**Tier 1 — silent wrongness**

1. **No discriminator in practice, and the only fallback is unsound.** IMP-011.
   Degrades the store before any query is written; a wrong field name and a wrong
   discriminator both answer `[]`, exit 0, and id-prefix filtering answers a
   superset. Cheapest fix in the list, because the advice is already shipped and
   already correct — the failure is delivery.
2. **The traversal root is unidentifiable in the result.** IMP-009's first option.
   `where` filters roots only, so the root cannot be excluded from `objects`;
   `traversal.depths` holds the fact out of band. Highest certainty, cheapest fix
   (one additive member, no 0.1 pin to break).
3. **"Which X have no Y?" answers yes to the wrong question.** IMP-012, second
   half. `$exists:false` is field absence, so the nearest-looking test on a
   relation returns *all* entities. The identical-looking field-absence question
   works, which teaches the wrong lesson. Not diagnosable — true as written — so
   it is teachable only.

**Tier 2 — cost and framing**

4. **Predicates are equality-only, and the guide never says where the surface
   stops.** IMP-012. No ranges, no field-to-field comparison, a call per edge type,
   and the two idioms that cover part of it (`order`+`limit` for max/min; set
   difference client-side) are undocumented beside the predicate.
5. **A provably contradictory condition answers with the empty set.** IMP-010. The
   trial's own number one; base rates argue it down — no contradictory predicate
   was written across three domains and 18 questions. Still worth keeping: it is
   the cheapest of the silent-set family to detect.
6. **The envelope's six members, as a shape question.** IMP-009's later options.
   Reframed: the measured cost is the root, not the taxonomy. As a
   regroup-it-properly question it is still a real conversation, but only if
   someone wants a nested envelope for its own sake.

**Tier 3 — teaching and finishing**

7. **`learn` has no section selector.** IMP-008. Real, but per-re-read rather than
   per-answer, and the only trial finding this exercise did not independently
   corroborate — its answerer read the guide out of the source file, not the CLI.
8. **A `$` key in the wrong place is refused as an unknown operator.** ISS-004.
   Accurate message, wrong destination; one call, one sentence.
9. **The `frontier` sentence stresses the rare case.** Folded into IMP-008. One
   sentence.
10. **No census verb.** IDE-003. A cost that scales with store size, not a failure.

### What the ranking changes

The trial ranked what hurt in one session; that is how a single-session account
should rank. With three stores and independent authorship the base rates move: the
trial's two leading findings (5, 8) fall to Tier 2 and the bottom, while the two it
treated as prose hygiene (1, 3) become the top and the third. Its envelope
complaint survives in a cheaper form (2, 6).

### What is deliberately not proposed

- **A `$prefix` operator.** Substring filtering is a workaround for the missing
  discriminator; making the workaround comfortable leaves the cause.
- **Range and cross-field operators.** Equality-only is a defensible design; this
  RFC asks for it to be *taught*, not widened. If it is ever widened, that is a
  design conversation of its own, and IMP-010's channel is where it starts.
- **A nested envelope as an end in itself.** Only the additive `roots` member is
  argued here on evidence; the restructure is optional.
- **Validation of `type`.** The store is permissive by design; the conventions set
  is advice. Nothing here asks for a schema.

### Sequencing

Waves are ordered by decision cost, not by size.

- **Wave 1 — no decision, measurable.** IMP-009's additive `roots` member (carve it
  out of the item if the rest of IMP-009 stays deferred); IMP-011's conventions
  content (the second-axis rule, the substring trap, the reason the discriminator
  matters); ISS-004 if refusal text is being touched anyway.
- **Wave 2 — one paragraph of teaching.** IMP-012 (the analysis boundary and the
  two idioms). Depends on nothing; makes two of the four stops cheaper without
  moving them.
- **Wave 3 — decisions, then shape.** IMP-010's diagnostic channel — and with it
  the store-side "no scanned root carries that field" diagnostic that makes
  IMP-011's consequence cheap — then IMP-009's restructure only if still wanted,
  then IMP-008's doors, which are more valuable after there is content worth
  reaching.
- **Unscheduled.** IDE-003.

IMP-003 (the 0.1.x batch) is unaffected; its rule — "a fix that is not in the guide
is not fixed" — is assumed by IMP-012 and IMP-011.

## Outcome

Open. The five questions this RFC cannot answer for itself:

1. **Is `type` the word?** Two of three independent authors wrote `kind`. Either
   the recommendation is wrong or it is unheard; the cure differs entirely.
2. **May an enumerating verb mention conventions at all** — a `declare` reply, a
   `learn` clause — or is advice forever opt-in? This is the delivery decision
   under IMP-011, and it is a product posture, not a text edit.
3. **Does the traversing envelope get `roots` now**, or does the whole response
   surface wait for the 1.0 conversation? The RFC argues now, because that member
   breaks no 0.1 caller.
4. **Is the analysis boundary permanent?** If ranges and aggregation are a
   deliberate non-goal, teach it once (IMP-012). If they are a roadmap, say so, and
   IMP-012's paragraph changes tense.
5. **Is a per-query diagnostic channel wanted at all** (IMP-010)? If not, three
   findings in Tier 1–2 lose their cheapest cure and become teaching only.

### Limits of the evidence

- n = 3 stores, one author each, 34 entities. Frequencies are indicative, not
  statistical; the *mechanisms* do not depend on the sample, the ordering does.
- The exercise's questions were authored without knowledge of the query language,
  but the exercise itself was designed by an agent that knew it — a milder form of
  the anchoring the design was trying to avoid.
- The one wrong answer came from a workaround the tool leaves an author, not from
  the query language.
- No effort estimates. Sequencing reflects product risk, not schedule.
